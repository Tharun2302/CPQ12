# Changelog

## Unreleased

### Added
- **Technical approvals now require Microsoft sign-in and record who approved.** Opening the Technical approval link shows "Sign in to approve" until the approver signs in with a CloudFuze Microsoft account (`AZURE_TENANT_ID`) whose email is in `team_approval_settings.technicalEmails`. The server enforces the same check on Technical approve, deny and comment, and saves `actedBy` (name and email from the verified sign-in) on approve or deny, so the Approval page tooltip shows "By: Name (email)". A sign-in counts only if Microsoft confirms it was issued to this app for a non-guest account, and it must be renewed after 12 hours. Overage deals still skip Technical automatically after the Team Lead approves. Team Lead and Legal steps are unchanged, and older approvals keep showing the shared mailbox. Set `TECH_APPROVER_SIGNIN_REQUIRED=false` to turn the check off (`technical-approver-guard.cjs`, `server.cjs`, `src/components/approval/TechnicalApproverSignIn.tsx`, `src/utils/technicalSignIn.ts`, `src/utils/approvalActor.ts`, `src/components/ApprovalPortalGate.tsx`, `tests/unit/technicalApproverGuard.test.ts`, `tests/unit/technicalApproverSignIn.test.tsx`, `tests/unit/approvalActor.test.ts`; design in `docs/design-technical-approver-signin.md`).
  - Not yet protected: the generic `PUT /api/approval-workflows/:id` can still change a Technical step without sign-in, and `PUT /api/team-approval-settings` can still edit `technicalEmails` without sign-in. Both are separate follow-ups.
  - Every Microsoft login now makes one extra call to Microsoft Graph (up to 5 seconds); if it fails, the login still works but cannot be used for Technical approvals.
- **Configure page: Migrate options can be combined in one quote.** The Migrate dropdown is now a tick list: any mix of Multi-Combination, Overage-Agreement and Data Sprawl can be ticked (one of each). The agreement is built on Multi-Combination when it is ticked, otherwise on Data Sprawl, otherwise on Overage; the other ticked options are added into that one document. Data Sprawl with Multi-Combination opens its own exhibit picker and one card per ticked exhibit, and uses the migration's Duration (Months) rather than a field of its own (unticking Multi-Combination carries that duration over as the Data Sprawl term); Overage with either opens Instance Type and Number of Instances, starting empty; it has no Duration of its own and runs for the quote's one Duration (Months): the migration's when Multi-Combination is ticked, else the Data Sprawl Duration (shown in the Overage section until a Data Sprawl exhibit is ticked). When Multi-Combination is ticked with Data Sprawl or Overage, that Duration is a common "Duration (Months)" card next to Customer Location and Common Instance Type, the combination panels lose their own Duration box, and every row is set to it (rows that differed start at the longest, the value the service term already used); Multi-Combination on its own keeps a Duration per panel. The Duration moves with the quote when options are ticked or unticked, and new Multi-Combination rows start at it. Both are priced flat (Data Sprawl at the Data Sprawl rates with no Manage licence; Overage as monthly instance price x that Duration x instances) and added to the plan cards, the custom plan total, the Data Sprawl card, the Quote page preview, approval amounts and the saved quote. One Discount applies to the combined total. In the agreement each part adds rows directly under the main agreement's own rows, i.e. after the last "CloudFuze Migrate" row on Multi-Combination or the last "CloudFuze Data Sprawl" row on Data Sprawl, above Managed Migration Service, Instance Type and Discount ("CloudFuze Data Sprawl" per exhibit, e.g. "Data Sprawl – DropBox (1,000 GB)", worded as on the Data Sprawl agreement, and "Server Instance", worded as the Overage Agreement template's own row, e.g. "2 Small Instance in a High-End Enterprise Server 3 Months"). With Data Sprawl on a Multi-Combination agreement, Important Payment Notes also gets the Data Sprawl agreement's line, e.g. "Overage Charge: $0.16 per GB | $1500 / month", as a bullet after the migration Overage Charges bullets), the Total Price includes them, and Data Sprawl exhibits are appended after the migration exhibits. What was typed for a part survives ticking or unticking another one; switching tab clears everything. Ticking a single option behaves as before (`src/components/MigrateOptionPicker.tsx`, `src/utils/migrateSelection.ts`, `src/utils/multiSprawl.ts`, `isMultiWithSprawl`/`overageAddOnCost`/`migrateAddOnTotal` in `src/utils/pricing.ts`, `src/components/MultiDataSprawlSection.tsx`, `src/components/OverageAddOnSection.tsx`, `src/hooks/useSprawlGroups.ts`, `src/components/ConfigurationForm.tsx`, `src/components/PricingComparison.tsx`, `src/components/QuoteGenerator.tsx`, `tests/unit/migrateSelection.test.ts`, `tests/unit/multiSprawl.test.ts`, `tests/unit/multiDataSprawlUI.test.tsx`, `tests/unit/multiSprawlAgreementDocx.test.ts`, `tests/unit/helpers/migratePicker.ts`).
- **Configure page: Data Sprawl agreements now ask for a Duration (Months).** Once a Data Sprawl exhibit is ticked, Project Configuration shows a required "Duration (Months)" box (whole months, 1 to 60) between the exhibit cards and Discount. It sets the agreement's Initial Service Term (`{{service_end_date}}`, and `{{service_term_label}}` e.g. "12-Months"); the price does not change. Choosing another agreement, another Migrate option or a different tab clears it. Manage Standalone and mange+sprawl keep the fixed "3-Month Free Trial", and Data Sprawl quotes saved before this change also keep it. Migrate and Bundle service terms are unchanged (`src/utils/serviceTerm.ts`, `sprawlTermIssue` in `src/utils/sprawlGroups.ts`, `src/components/ConfigurationForm.tsx`, `src/components/QuoteGenerator.tsx`, `tests/unit/serviceTerm.test.ts`, `tests/unit/dataSprawlServiceTermUI.test.tsx`).
- **Approval page: each card now shows how long every approval stage took.** Under Team, Tech and Legal (and MM/AM when present) the card shows the time that stage took (e.g. "2h 15m"), "waiting X" under the step still open (updates once a minute), and "rejected after X" in red for a rejected step. The right of the "Current" line shows "Total" when finished or "Total so far" while open. A stage starts when the previous stage was decided (the first starts when the approval was created); times come from the server stamp saved on each approve or reject. Old or out-of-order records, steps with missing or duplicate numbers, and approvals cancelled by the requester show "—" instead of a wrong number. Hovering a step now also shows its real decision time. Frontend only, no API or database change (`src/utils/approvalTiming.ts`, `src/hooks/useMinuteClock.ts`, `src/components/approval/ApprovalStepTime.tsx`, `src/components/ApprovalDashboard.tsx`; design in `docs/design/approval-step-timing.md`).
  - Step times can still be set by the generic create/update approval routes, so treat them as display only until those routes lock `workflowSteps`.

### Fixed
- **Agreements: "Select Basic" / "Select Standard" now use that plan's exhibits for every combination.** The plan page saves a Standard exhibit plan for each Multi-Combination combination as soon as it opens, and agreement generation gave that saved value priority over the plan card clicked, so a Basic agreement was built from Standard exhibits (or, with the plan check above, could end up with none). Per-combination exhibit plans now travel only with "Proceed with Custom Plan Selection" (`exhibitPlans` on the selected calculation) instead of being read from `sessionStorage`; a plan card sends none. They are matched to exhibits by picker folder, so a combination's Include and Not Include always get the same plan (`exhibitPlanResolver` in `src/utils/exhibitPlan.ts`, `src/types/pricing.ts`, `src/components/PricingComparison.tsx`, `src/components/QuoteGenerator.tsx`, `tests/unit/exhibitPlan.test.ts`, `tests/unit/pricingPlanExhibitCheck.test.tsx`).
- **Agreements: custom plans keep each combination's exhibit plan.** On "Proceed with Custom Plan Selection", the later merge filters compared every exhibit with the headline plan only, so a combination set to Basic inside a Standard quote had its Basic exhibits replaced and then dropped. Every filter now uses the plan chosen for that exhibit's combination (`src/components/QuoteGenerator.tsx`).
- **Agreements: combinations such as "Box to Microsoft(OneDrive&SharePointOnline)" no longer disappear when another combination is selected.** An exhibit named "X to Y (A & B)" was treated as a combined exhibit and dropped whenever any other exhibit with the same plan and include type was in the agreement, even an unrelated one such as Box to OneDrive. It is now only replaced by a dedicated exhibit of the same source and destination (e.g. "Dropbox to Google MyDrive" for "Dropbox to Google(MyDrive & ShareDrive)"); names without "X to Y" before the bracket are never dropped this way (`combinedExhibitFamily`, `inCombinedFamily` in `src/utils/exhibitCombination.ts`, `src/components/QuoteGenerator.tsx`, `tests/unit/exhibitPlan.test.ts`).
- **Deal Desk email: the attached agreement carries the chosen plan's exhibits.** The email flow only expanded the exhibits ticked on Configure to their same-plan siblings, so Standard exhibits ticked before choosing Basic were dropped without the Basic ones being added. It now adds the chosen plan's Include and Not Include exhibits for each ticked combination (`src/components/QuoteGenerator.tsx`).
- **Agreements: exhibits come only from the selected plan.** A plan missing one of its Include / Not Include exhibits used to borrow it from the other plan. For example, a Standard Box to Google (MyDrive&ShareDrive) agreement, which has no Standard Not Include exhibit, carried the "Basic Not Include" exhibit. Exhibits are now taken only from the selected plan (or a per-combination plan override); a variant the plan does not have is left out. This also applies to the exhibit picker's auto-selection. Exhibits ticked on Configure before the plan was chosen no longer slip through either: when nothing matched the plan, generation fell back to the raw ticks, so a Basic Box to Microsoft(OneDrive&SharePointOnline) agreement carried its only exhibit, Standard Include. A final check now drops any exhibit of another plan from the agreement and from the agreement emailed to Deal Desk. On the plan page, "Select Basic" / "Select Standard" and "Proceed with Custom Plan Selection" now refuse a plan that a selected combination has no exhibits for, with a popup naming it (e.g. "There are no Basic plan exhibits for: - Box to Microsoft(OneDrive&SharePointOnline)"), and stay on the page; 22 combinations have no Basic exhibits today, e.g. Dropbox to Google(MyDrive & ShareDrive), Gmail to Outlook and the Sprawl combinations. The page loads the exhibit list for this; if it cannot, the check is skipped. As a safety net, agreement generation shows the same popup and leaves such combinations without exhibits. Exhibits with no plan and per-combination plan choices are unchanged (`src/utils/exhibitPlan.ts`, `src/components/PricingComparison.tsx`, `src/components/QuoteGenerator.tsx`, `src/components/ExhibitSelector.tsx`, `tests/unit/exhibitPlan.test.ts`, `tests/unit/exhibitPlanSelection.test.tsx`, `tests/unit/pricingPlanExhibitCheck.test.tsx`).
- **Approvals: the Technical step can only be decided by a signed-in Technical approver.** The Microsoft sign-in was enforced on the approve/deny step route, but two other routes could still record a Technical approval without it: creating a workflow took each step's status from the request body, and the generic workflow update (`PUT /api/approval-workflows/:id`) could overwrite the Technical step inside `workflowSteps` or mark the whole workflow approved. With sign-in enforced (`TECH_APPROVER_SIGNIN_REQUIRED` not `false`), a new workflow now always starts with the Technical step pending; the generic update keeps the Technical step exactly as stored (an altered, removed or dotted-path change is ignored and logged) and refuses `status: approved` with 409 `TECH_NOT_APPROVED` while the Technical step is not approved; and a Technical decision made between that update's read and write gives 409 instead of being overwritten. Infra team / QA steps, client approval, cancelling and denial keep working through the same route (`withPendingTechnicalStep`, `protectTechnicalStep` in `technical-approver-guard.cjs`, `server.cjs`, `tests/unit/technicalApproverGuard.test.ts`).
- **Configure page: a browser refresh starts the quote over.** Refreshing the Configure page used to bring back the previous Migrate options, ticked exhibits ("Selected combinations"), inputs, per-combination plans and discount, because they are kept in the tab's session. A refresh (F5) on /configure now clears them before the app loads, so the page opens fresh; contact details and the deal are kept. Moving between Configure, Quote and back keeps everything as before, and refreshing the Quote page still keeps the quote so its agreement can be generated (`src/utils/configureReload.ts`, `src/main.tsx`, `tests/unit/configureReload.test.ts`).
- **Multi-Combination agreements: Important Payment Notes bullets line up.** The template mixes two bullet lists there, so "Overage Charges for …", "Initial Service Term" (and the added Data Sprawl overage line) sat further right, with a larger marker, than the first three bullets. On generated Multi-Combination agreements every bullet in that section now uses the first bullet's list, indent and spacing; the text and its bold are unchanged, and the empty spacer lines (and an empty bullet left by the template's loop) are removed so the spacing is even. The template itself is not changed (`alignPaymentNoteBullets` in `src/utils/docxTemplateProcessor.ts`, `src/components/QuoteGenerator.tsx`, `tests/unit/multiSprawlAgreementDocx.test.ts`).
- **Deal page: Contact and Company now load from HubSpot instead of showing "Not Available".** The Deal page only used the values in the HubSpot "Open Zenop.ai" link, which is a snapshot taken when the link was made. Deals whose contact or company were added later (or renamed) showed "Not Available" or an old deal name. Once the user is signed in, the page now asks the server for the deal's current primary contact and company and fills them in, keeping the link values where HubSpot has nothing. Stage and close date still come from the link. Fake placeholder values (a 555 phone, "Address from HubSpot", "hubspot.com") are no longer put into client info for missing fields (`hubspot-deal-details.cjs`, `server.cjs`, `src/utils/hubspotDealDetails.ts`, `src/components/RefreshDealOnSignIn.tsx`, `src/App.tsx`, `tests/unit/hubspotDealDetails*.test.ts`, `tests/unit/refreshDealOnSignIn.test.tsx`).
  - `GET /api/hubspot/deals/:dealId` now requires sign-in, accepts only numeric IDs, is limited to 100 requests/minute, and returns `details` (resolved deal, contact and company fields) next to the raw deal in `data`. It returns 503 when no HubSpot key is set, 404 for an unknown deal and a generic 502 for other HubSpot errors.
  - The Company Name card now falls back to the link's `CompanyName` when `CompanyFromContact` is empty (e.g. the Wavenet deal showed "Not Available" although the link had `CompanyName=Wavenet`). This works without a HubSpot key. "Extracted from email domain" now shows only when the name really came from the email (`src/components/DealDetails.tsx`, `tests/unit/dealDetailsCompanyName.test.tsx`).
  - **Needs `HUBSPOT_API_KEY`** (a HubSpot private-app token with read access to deals, contacts and companies) on the server. Without it the page keeps today's behaviour. Production currently reports HubSpot as "Demo mode".
- **Exhibit sync folder: `EXHIBITS_SYNC_DIR` written with backslashes is now checked the same way on Linux as on Windows.** On Linux, a value like `..\outside` was read as one folder name inside the project instead of "one folder up", so it was not rejected, and `exhibitSyncDir` tests failed in the pull-request CI. Backslashes are now treated as folder separators on every platform, so `..\outside` falls back to `backend-exhibits` and `local\exhibits` means `local/exhibits` (`exhibit-sync-dir.cjs`, `tests/unit/exhibitSyncDir.test.ts`).

Preview, the completion email and bulk download still include the certificate, and signing, status and the stored executed PDF are unchanged. If Zoho cannot be reached, Download serves the stored copy with the certificate rather than failing. It now says "This approval was cancelled by the requester." (also the server's 409 message if Approve is clicked on an old page). After the requester deleted the approval, the link opened an empty dashboard with no message. It now shows "This approval request was deleted by the requester." and stops retrying.   - Discounts are now capped at 100% (main and custom-items discount). Above 100%, the quote total went negative.

  - The Deal Desk and agreement emails now show the same discount % and amount as the quote page.
  - Removed an old Quote page message about a "$2,500 minimum / 10% cap" that no longer exists.

The emails then showed the discounted amount as the "Subtotal" (e.g. Subtotal $8,000, Discount −$2,000, Final $8,000), and the agreement could take the discount off a second time. The custom plan now passes on the full price. - **Data Sprawl: one project configuration per selected exhibit.** On Manage → Data-Sprawl and MANAGE + Sprawl, selecting two Content Sprawl exhibits (e.g. DropBox and Egnyte) showed only one configuration, because groups were built per sprawl type from manual checkboxes.
